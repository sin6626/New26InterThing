# 后端代码阅读指南

适合第一次接触这个后端时按顺序阅读。先看文件开头的“阅读导航”，再看函数附近的“为什么”注释；不要尝试从 80 个文件的第一行连续读到最后一行。

## 先认识四类文件

- `main.ts`：把模块接起来，像总接线图。它不应该藏具体的水泵安全阈值判断。
- `http.ts`：接收浏览器请求、验证参数、把任务交给模块。它不直接决定设备是否安全。
- `flows/`：业务步骤与调用顺序，例如“检查→发 MQTT→记录日志”。
- `state/`、`rules/`、`adapters/`：分别保存运行状态、计算判断条件、处理 MySQL/HTTP/设备协议。

`index.ts` 是模块给外面看的入口。如果只想知道一个功能能被如何调用，先看它；想知道实现细节，再进入对应目录。

## 从一条设备数据开始

```text
MQTT device/sensor
→ main.ts 分流
→ realtime/adapters/sensor-message.ts 解析 online
→ realtime/flows/receive.ts 保存历史
→ online=0 才刷新在线、广播、驱动自动控制与水力诊断
→ online=1 只补齐历史，不能让旧数据控制现在的设备
```

设备报文的 `c_time` 用于历史记录；自动控制使用服务器收到实时包的时间判新鲜度。这样断网补发的旧温度不会被误当成当前温度。

## 从一次“打开水泵”开始

```text
浏览器 POST 指令
→ control/http.ts 验证请求形状
→ control/flows/execute.ts 读取数据库配置并校验值
→ automation/flows/manual.ts 与 safety/state/supervisor.ts 授权
→ control/adapters/command.ts 把 on 映射为设备协议 JSON
→ infrastructure/mqtt/sensor-mqtt.ts 发布
→ control/adapters/mysql.ts 保存当前值与操作日志
```

`pump/heater` 是设备运行指令；`master` 切换后端自动模式；PID 和安全参数只存数据库。MQTT 的“发布成功”仅指 Broker 接收，设备是否执行要看之后的设备实际反馈。

## 看自动控制和安全故障

`automation/flows/engine.ts` 保存单设备运行状态，`mode.ts` 负责启停自动模式，`demand.ts` 计算加热需求。安全判断在 `safety/state/supervisor.ts`，每类条件在 `safety/rules/` 独立文件。保护结论由 `automation/flows/protection.ts` 落实为关热、冷却和停泵，并通过 `fault/report.ts` 入库告警。

看任何保护都要区分：`desiredPump/desiredHeater` 是后端期望；`actualPump/actualHeater` 是设备实际反馈。发了开泵指令并不表示已经建流。故障一旦锁定，也不会因为一包正常数据自动复位。

## 常见代码写法

- `async/await`：等待数据库、MQTT 或 HTTP 操作完成；`await` 顺序影响安全动作顺序。
- `Promise<void>`：操作会异步完成，但没有业务返回值；失败仍可能抛异常。
- `createXxx(dependencies)`：把数据库、时钟或发布函数从外部注入，测试时可以换成假的实现，不会碰真实设备。
- `interface/type`：说明一段流程需要哪些事实；它们本身不会执行任何业务动作。
- `null`：该字段当前无有效读数，不能直接当零；安全规则通常会先检查新鲜度。

修改控制或保护条件时，先找对应 `rules/`，再确认 `state/` 的持续时间窗口、`flows/` 的动作顺序和相关测试。不要只改中文故障描述或页面按钮。
