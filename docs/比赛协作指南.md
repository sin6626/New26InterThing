# 比赛协作指南

这份指南用于让本地小模型在比赛现场安全地排查和修改 `New26InterThing`。它不是业务需求文档；项目事实以代码、`AGENTS.md`、本目录的现场手册和 API 文档为准。

## 建议的上下文顺序

每次新会话只提供完成当前任务所需的内容，避免一次塞入整个仓库：

1. 根目录 `AGENTS.md`。
2. 本文件。
3. `docs/比赛现场运行手册.md`。
4. 涉及接口时再提供 `docs/API.md`。
5. 涉及智能识别时读取 `docs/智能识别模版使用.md`。
6. 涉及后端时先看 `docs/后端模块目录.md` 和 `docs/后端代码阅读指南.md`。
7. 最后用 `rg` 找到当前问题涉及的代码和测试，不要让模型通读所有文件。

9B 模型上下文和推理能力有限。一次只交给它一个明确问题，例如“修复干烧计时被错误重置”，不要同时要求改页面、改数据库、重构目录和补文档。

## 推荐工作流程

### 只排查、不修改

```text
请只诊断，不要改代码。现象是：<现象>。
先给出 3 个按概率排序、可以验证的原因；然后用现有测试、日志、只读 HTTP 或只读 SQL 验证。最后告诉我根因、证据和建议，不要凭感觉下结论。
```

排查优先顺序：

1. `git status --short`，确认工作区是否已有修改。
2. 用 `rg -n "关键词" apps packages docs` 找实际入口。
3. 找相邻测试，建立能够复现用户现象的最小测试。
4. 页面问题先看浏览器请求日志和 WebSocket 状态。
5. 设备问题依次核对 HTTP、WebSocket、MQTT、数据库和设备实际反馈。
6. SQL 默认只允许 `SELECT`、`SHOW`、`DESCRIBE`；需要写库必须先说明影响。

### 修复代码

```text
请修复：<单一问题>。
先写一个能复现该问题的失败测试并运行，确认它因目标问题失败；再做最小修复。完成后运行相关测试、全量测试和 pnpm typecheck，不运行 pnpm build。更新必要文档并提交，最后解释修复逻辑。
```

每次修改遵循：测试变红 → 最小修复 → 定向测试变绿 → 全量测试 → 类型检查 → 检查 diff → 中文提交。

## 系统关键事实

- 前端：`apps/web`，Nuxt 4、Vue 3、Element Plus。
- 后端：`apps/server`，Express、MySQL、MQTT、WebSocket，所有自动控制与保护决策都在这里。
- 共享类型：`packages/shared`。
- `contest_admin` 只与本项目共用 MySQL，不调用本项目 HTTP API。
- `pump`、`heater` 才是设备运行指令；`master` 只切换后端自动模式，PID 和阈值等参数只保存到数据库。
- `desiredPump/desiredHeater` 是后端期望；`actualPump/actualHeater` 是设备反馈，两者不能混为一谈。
- MQTT 发布成功只表示 Broker 收到，不表示设备已经执行。
- `online=0` 是实时数据；`online=1` 是补发历史，不能驱动当前控制。
- 故障锁定期间禁止重新开启自动模式，但关闭加热、停止水泵和“重新发送关闭”仍允许执行。
- 一个故障周期只锁存第一个主故障；已有故障未复位时，其他规则可能只作为并发事实，不会再弹出第二个主故障。
- 调试模式只用于模拟，后端重启后关闭；连接真实设备或验证保护时必须关闭。

## 安全规则修改检查表

修改 `apps/server/src/modules/safety/` 或 `automation/` 前，必须回答：

1. 规则使用的是实际状态还是期望状态？
2. 计时从什么事实成立时开始？什么情况暂停、清零或锁存？
3. 没有新 MQTT 数据时，`tick()` 是否仍会推进或触发传感器超时？
4. 规则关闭后，是只停止记录/弹窗，还是连保护也停止？
5. 故障发生后应关热、立即停泵，还是保留限时散热？
6. 是否会被已有的首个锁定故障遮挡？
7. 是否有边界测试：刚好达到阈值、短暂抖动、断线、复位、人工模式和自动模式？

不要只修改页面文案来“修复”安全问题，也不要用前端定时器代替后端保护。

## 常用命令

```powershell
git status --short
rg -n "关键词" apps packages docs
pnpm --filter @new26interthing/server test -- 测试文件名.test.ts
pnpm --filter @new26interthing/web test -- 测试文件名.test.ts
pnpm test
pnpm typecheck
git diff --check
git diff
```

不要默认执行 `pnpm build`。不要为了让测试通过而连接真实设备或发布 MQTT 指令；使用依赖注入和 mock。

## 必须停下来问人的情况

- 赛方只给了示例值，没有给字段类型、枚举或完整响应结构。
- 不知道某个 MQTT 数字代表什么，或设备端 `0/1` 含义不确定。
- 需要修改既有数据库表结构或删除生产数据。
- 需要关闭核心安全规则、降低阈值或绕过保护来开启设备。
- 工作区已有修改与当前任务重叠，无法确认哪些属于用户。
- 测试与真实设备表现冲突，但没有报文、日志或数据库记录作为证据。
