# 第七里程碑：水循环状态机、时间比例 PID 与累计量

[返回重构计划目录](../重构计划.md)

### 目标

建立“`master` 切换后端自动模式 → 状态机根据实时传感器数据推进 → 只通过统一执行器接口控制水泵和加热 → 页面展示运行状态”的闭环，并完成时间比例 PID 与累计水量。`master` 本身只保存为后端模式配置，不发布 MQTT；设备运行指令仍只有 `pump` 和 `heater`。

本里程碑完成自动控制的运行骨架和可测试计算，但不提前吞并第八里程碑的持续安全保护。生产环境继续禁止真正开启加热，直到第八里程碑完成后通过同一安全门放开。

### 已确认业务边界

- 比赛系统最多只有一台设备，自动控制状态按该设备维护，不设计多设备调度器。
- `master=on/off` 只表示启用或停止后端自动状态机，保存到 `t_direct_global`，不发送 MQTT。
- `pump`、`heater` 是仅有的设备运行指令，继续复用第六里程碑的协议适配、QoS 1 单次发布、超时、回环过滤和操作日志。
- 目标温度、控温策略、PID 参数、建流时间、冷却时间、管径等均从 `t_direct_config + t_direct_global` 动态读取，只供后端判断，不发送 MQTT。
- 自动控制只消费后端已经解析、校验并成功保存的实时传感器读数，不另建 MQTT 订阅或旁路解析。
- 期望状态与设备实际状态分离：发布成功只更新期望状态；实际水泵/加热状态只认设备传感器报文中的 `water_Y2`、`heat_Y1`。
- 累计水量使用现有 `t_water_flow_accumulator`，不新增或修改数据库表结构。
- 累计量只包含累计过水体积、最近一分钟平均流量和管内流速；旧项目基于本地 JSON 文件的累计运行时长不迁移。

### 状态机

本里程碑的正常路径使用四个状态：

1. `STOPPED`：自动模式关闭，期望水泵和加热均为关闭。
2. `BUILDING_FLOW`：`master=on` 后先下发水泵开启，等待设备实际开泵且流量达到 `min_safe_flow`。
3. `RUNNING`：建流成功，按 `temperature_control_strategy` 计算加热期望值。
4. `COOLING`：停止时先关闭加热，水泵继续运行 `cooling_delay` 秒，再关闭水泵并回到 `STOPPED`。

状态转换规则：

- `STOPPED → BUILDING_FLOW`：配置合法、最近传感器数据可用且水泵开启发布成功。
- `BUILDING_FLOW → RUNNING`：设备实际水泵开启，且有效流量达到最低流量。
- `BUILDING_FLOW → STOPPED`：超过 `build_flow_timeout` 仍未建流，关闭水泵、保持 `master=off`，记录启动失败；第八里程碑再把它升级为完整故障联锁。
- `RUNNING → COOLING`：用户设置 `master=off`、自动运行被主动停止，或自动控制内部发生不可继续的发布错误。
- `COOLING → STOPPED`：冷却倒计时结束后水泵关闭成功。
- 重复设置相同模式必须幂等，不重复发布水泵或加热指令。

本里程碑不建立正式 `FAULT` 状态。超温、超压、持续失流、传感器超时、干烧、温度传感器装反和故障复位属于第八里程碑。

### 自动控制深模块

新增 `modules/automation`，对 HTTP、MQTT 回调和定时器只暴露一个小接口：

```ts
interface AutomationEngine {
  setEnabled(enabled: boolean): Promise<AutomationSnapshot>
  handleReading(reading: AutomationReading): Promise<void>
  tick(): Promise<void>
  getSnapshot(): AutomationSnapshot
  close(): Promise<void>
}
```

- `setEnabled()` 隐藏启动、停止、状态转换、模式持久化和执行器顺序。
- `handleReading()` 接收规范化后的单设备传感器数据，更新实际执行器状态、推进建流并驱动 PID 计算。
- `tick()` 使用可注入单调时钟推进建流超时、PID 窗口和冷却倒计时；生产环境每秒调用一次，测试直接控制时间，不使用真实等待。
- `getSnapshot()` 返回不可变页面快照，不暴露内部队列、计时器或可变状态。
- `close()` 停止调度器，并在服务退出时执行安全的关闭流程。

内部拆分：

- `automation-engine.ts`：唯一状态机所有者，只负责转换和协调。
- `control-config.ts`：读取并校验动态控制参数，兼容已确认的旧 topic 别名。
- `actuator.ts`：复用第六里程碑命令适配和 MQTT 发布能力，串行化水泵/加热动作并记录日志。
- `temperature-controller.ts`：统一回差控制与时间比例 PID，两种策略都只返回期望动作，不直接访问 MQTT 或数据库。
- `automation.scheduler.ts`：唯一生产定时器，调用 `tick()`；状态机实现内部不自行创建定时器。

### 配置读取与校验

启动自动模式前一次性读取当前配置，运行过程中在配置版本变化后于安全窗口重新加载。至少校验：

- `temperature_control_strategy` 只能是 `hysteresis` 或 `pid`。
- 目标温度必须低于最高安全温度；温度回差必须大于 0 且小于目标温度。
- `min_safe_flow`、`build_flow_timeout`、`cooling_delay`、`data_timeout`、`command_timeout` 和管径必须为正数。
- PID 的 `Kp/Ki/Kd` 必须是有限非负数，使用 PID 启动时 `Kp > 0`。
- PID 周期、最短开启和最短关闭时间必须为正整数，并满足周期不小于最短开启与最短关闭之和。
- PID 超调关断温度必须低于最高安全温度，恢复回差必须小于目标温度。

配置非法时拒绝启动，返回具体字段和中文原因，不下发任何开启指令。运行中修改配置不应重建引擎或丢失累计量；PID 关键参数变化时在下一个控制窗口重置积分状态。

### 回差控制与时间比例 PID

- `hysteresis`：出口温度低于 `target_temperature - temperature_hysteresis` 时请求加热，高于或等于目标温度时请求关闭。
- `pid`：以出口温度为测量值，按真实单调时间计算 P/I/D，输出限制在 `0%–100%`。
- 时间比例输出把一个 `pid_cycle_time` 窗口切成前段开启、后段关闭，例如 40% 表示该窗口前 40% 请求开启。
- 使用测量值微分，避免目标值变化造成微分冲击；积分必须做抗饱和。
- 执行 `pid_min_on_time`、`pid_min_off_time`，不足最短脉冲时舍弃或缩短本窗口，不产生继电器抖动。
- 超过 `target_temperature + pid_overshoot_allowance` 时立即把期望加热设为关闭；降到恢复阈值前不重新请求开启。
- PID 输出、计划占空比、窗口剩余时间、限制原因和计算错误进入状态快照，供页面调试。

第七里程碑允许计算和展示加热期望值，也允许测试适配器验证真实下发顺序；生产适配器中的“加热开启安全门”继续返回禁止开启。第八里程碑完成后只替换安全门判定，不改状态机或 PID 接口。

### 累计水量

新增 `modules/water-flow`，消费与状态机相同的规范化实时数据：

- 瞬时流量单位为 `L/min`，相邻有效采样采用梯形积分，累计结果单位为 `L`。
- 只有 `0 < Δt <= data_timeout` 时累计；乱序、重复时间、负流量或断线长间隔不累计。
- 最近一分钟平均流量使用服务端接收时间窗口计算。
- 管内流速按后台配置的 `pipe_inner_diameter` 换算，未配置或非法时明确返回 `unconfigured`，不猜默认管径。
- 内存状态按固定节流间隔 UPSERT 到 `t_water_flow_accumulator`，进程启动时恢复。
- 提供人工清零接口，事务保存为 0 并在 `t_direct_history` 记录旧值、结果和备注；清零不发送 MQTT。

### 与现有实时链路集成

`sensor-realtime-handler` 在传感器数据成功入库后，按固定顺序调用：

1. 广播原始 `sensor.realtime`。
2. 把同一个规范化读数交给累计水量模块。
3. 把同一个规范化读数交给自动控制引擎。

自动引擎和累计模块的失败必须记录清晰错误，但不能阻止已经成功保存的传感器数据广播。所有异步控制动作通过单设备串行队列执行，避免传感器消息与 `tick()` 同时发布相反指令。

WebSocket 新增两类共享消息：

- `automation.status`：状态机、模式、倒计时、实际/期望执行器状态、PID 诊断和最近发布结果。
- `water-flow.realtime`：瞬时流量、分钟平均流量、管内流速、累计水量和更新时间。

页面首次进入必须通过 HTTP 获取快照，WebSocket 只负责后续更新，不能要求用户切换路由才能看到状态。

### HTTP 接口

- `GET /api/automation/:deviceNumber`：读取自动控制和累计水量完整快照。
- `POST /api/automation/:deviceNumber/start`：等价于设置 `master=on`，由后端启动状态机；生产环境在第八里程碑前返回“加热安全保护尚未完成”的受限运行说明，但允许完成水泵建流和状态演练。
- `POST /api/automation/:deviceNumber/stop`：设置 `master=off`，执行“先关热、后冷却、再关泵”。
- `POST /api/automation/:deviceNumber/water-flow/reset`：清零累计水量并记录操作日志。

指令页面切换 `master` 时仍调用现有 `POST /api/controls/commands`。`control.service` 对 `master` 委托给 `AutomationEngine.setEnabled()`，不直接发布 MQTT；专用 start/stop 接口供状态面板和测试复用同一个深模块，不复制业务逻辑。

### 前端页面

继续复用 `/controls`，不新增重复的“自动控制配置页”：

- 在指令树上方增加自动运行状态面板，展示模式、状态机文本、倒计时和最近发布结果。
- 展示水泵/加热“实际状态”和“期望状态”，不把 Broker 发布成功伪装成设备执行成功。
- 展示控温策略、出口温度、目标温度、PID 输出、计划占空比、窗口剩余时间和限制原因。
- 展示瞬时流量、最近一分钟平均流量、管内流速、累计水量，并提供清零按钮。
- `master` 开关调用后端状态机；状态转换期间锁定，成功后显示“修改成功”，失败后恢复后端快照。
- 页面首次加载 HTTP 快照，后续订阅现有单例 WebSocket；离开页面只移除自己的监听，不关闭全局连接。

- `AutomationState`、`AutomationMode`、`ActuatorState`。
- `AutomationSnapshot`、`PidSnapshot`、`WaterFlowSnapshot`。

### 测试 seam

- 状态机 seam：正常启动、建流成功、建流超时、幂等启动、主动停止、冷却倒计时和发布失败。
- 执行器 seam：启动先开泵、停止先关热、冷却后关泵、同值去重、动作串行、`master` 永不发布 MQTT。
- 配置 seam：动态读取、topic 别名、非法数字、交叉约束、运行中配置变化和 PID 重置。
- 控温 seam：回差上下阈值、PID P/I/D、抗饱和、超调抑制、时间窗口、最短开关时间和单调时钟。
- 累计量 seam：梯形积分、首次样本、重复/乱序时间、断线长间隔、分钟平均、流速换算、持久化恢复和清零审计。
- 实时集成 seam：传感器先入库和广播，再分发给累计量与自动引擎；派生模块失败不吞掉实时消息。
- HTTP/WebSocket seam：首次快照、启停、清零、统一错误状态和两类实时消息。

状态机、PID 和累计算法的测试必须使用可注入时钟和假发布器，不使用真实等待、真实 MQTT 或真实设备。

### 验收场景

1. 修改目标温度、PID、超时或安全阈值只更新 `t_direct_global`，不产生 MQTT 消息。
2. 切换 `master=on` 不发布 master 指令；状态机只尝试开启水泵并进入 `BUILDING_FLOW`。
3. 设备实际开泵且流量达标后进入 `RUNNING`，PID/回差控制持续生成可解释的加热期望值。
4. 第八里程碑前，生产环境始终拒绝真正发布 `heater=on`，但 PID 调度和状态展示可完整演练。
5. 停止自动模式时先关闭加热，冷却倒计时结束后只关闭一次水泵，并回到 `STOPPED`。
6. MQTT 断开或发布超时不离线排队、不重试旧的开启动作，页面显示最近失败原因。
7. 连续有效流量数据正确增加累计水量；断线、乱序和非法数据不虚增，重启后从现有表恢复。
8. 页面首次进入即显示 HTTP 快照，WebSocket 更新无需切换路由；1366×768 与 1920×1080 无横向溢出。
9. 运行相关单测、完整测试、类型检查和真实 MySQL 只读/受控写入联调；按约定不执行生产构建。

### 明确不做

- 不在第七里程碑启用生产环境加热开启；第八里程碑完成持续安全门后再放开。
- 不实现超温、超压、持续失流、干烧、温度传感器装反、传感器超时的完整故障判定和复位流程。
- 不迁移旧项目把状态机、安全保护、故障诊断和 MQTT 发布堆在一个大文件里的实现。
- 不使用本地 JSON 文件保存累计运行时长，不新增累计运行时长表。
- 不新增设备 ACK 协议，不把 PUBACK 当作实际执行状态。
- 不修改现有数据库表结构，不恢复多设备控制模型。
