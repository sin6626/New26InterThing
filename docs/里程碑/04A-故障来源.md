# 第四里程碑补充：故障来源

[返回第四里程碑](./04-设备故障信息.md)

## 目标

在故障记录中增加明确的“错误来源”，固定只有两种业务值：

| 内部值 | 页面名称 | 含义 |
| --- | --- | --- |
| `system` | 系统判定 | 后端现有安全保护、设备离线、水力诊断和确定性规则产生的故障 |
| `intelligence` | 智能判定 | 比赛方智能判定接口明确返回故障结论后产生的故障 |

“来源”只说明故障由谁判定，不替代现有 `type`。`type` 继续表示原有告警/错误分类，`e_no` 继续表示故障编号。

## 已确认边界

1. 当前所有本地规则调用 `reportFault()` 产生的故障均属于“系统判定”。
2. 智能识别目前只把赛方响应按动态映射写入 `t_behavior_data`，尚未取得“是否故障、错误码、错误类型、错误说明”等正式字段定义。
3. 未取得赛方接口文档前，只完成来源存储、查询、筛选和展示能力；不从行为字段名称、中文文本或任意真假值猜测故障。
4. 只有赛方响应明确表示“判定为故障”时，才新增一条来源为 `intelligence` 的故障记录；正常、未知、字段缺失、解析失败均不写故障表。
5. 智能判定故障可以进入故障页面并触发统一右上角警告，但不因此获得安全控制权。是否自动停机必须由后端确定性安全规则决定，除非赛方另有明确要求。

## 数据库方案

现有 `t_error_msg` 没有来源列，且项目约定不修改既有表结构，因此不在 `t_error_msg` 增加字段，也不把来源塞进 `e_msg` 或复用 `type`。

新增旁表：

```sql
create table if not exists t_error_source (
  fault_id int not null,
  source varchar(32) not null,
  primary key (fault_id),
  index idx_error_source_source (source)
);
```

约束：

- `fault_id` 对应 `t_error_msg.id`，一条故障最多一个来源；
- 应用层只允许写入 `system`、`intelligence`；
- 不增加数据库外键，避免影响现有后台和旧数据维护；
- 新故障写入 `t_error_msg` 与 `t_error_source` 必须处于同一事务，任一步失败都回滚，不能出现新记录来源丢失；
- 既有 `t_error_msg` 没有旁表记录时，查询统一返回 `system`，因此无需批量回填旧数据；
- 提供独立迁移脚本和根目录命令，现场首次启动新版前手动执行；不让应用启动时偷偷改表。

## 后端计划

### 领域类型与统一入口

1. 在共享类型中增加 `FaultSource = 'system' | 'intelligence'`。
2. `FaultItem`、`FaultQuery` 和 `FaultOptions` 增加来源字段或筛选项。
3. `FaultReport` 增加必填 `source`，避免新增调用方忘记声明来源。
4. 将当前所有确定性调用点逐一改为 `source: 'system'`，包括：
   - 设备离线；
   - 温度、压力、流量及传感器超时保护；
   - 水力联合诊断；
   - 其他调用统一 `reportFault()` 的本地规则。
5. `FaultReporter` 仍是唯一故障入库入口；智能识别不得绕过它直接写 SQL。

### 仓储查询

1. `save()` 在事务中先写 `t_error_msg`，再用新 ID 写 `t_error_source`。
2. 列表通过 `left join t_error_source` 返回：
   `coalesce(t_error_source.source, 'system') as source`。
3. 来源筛选使用相同的 `coalesce` 表达式，保证旧记录能够被“系统判定”筛中。
4. 列表 count、分页 rows 和统计接口必须复用同一来源筛选条件。
5. `GET /api/faults/options` 返回固定的两个来源选项，不依赖数据库中是否已有智能记录。
6. 故障类型统计图继续按 `type` 统计，但必须服从当前来源筛选条件；本次不额外增加第二张来源统计图。

### HTTP 接口

现有三个接口保持路径不变：

- `GET /api/faults/options`
- `GET /api/faults`
- `GET /api/faults/statistics`

列表和统计增加可选查询参数：

```text
source=system | intelligence
```

非法来源返回 HTTP 400。响应继续使用 `{ code, message, data }`，并同步更新 `docs/API.md`。

## 智能判定接入计划

### 第一阶段：现在可以完成

- 完成来源类型、旁表迁移、统一故障入口、查询筛选和页面展示；
- 当前所有新增故障来源固定为 `system`；
- 智能识别仍只保存行为数据，不产生智能故障。

### 第二阶段：取得赛方文档后实施

必须由用户向赛方确认以下内容，缺一项就停止接入：

1. 哪个字段表示是否判定为故障，以及所有可能值；
2. 故障编号字段和编号全集，是否与 `t_error_code_mapper.e_no` 共用；
3. 故障类型字段和枚举，是否继续使用当前 `type`；
4. 一次响应可能返回一个还是多个故障；
5. 故障说明字段是否可信，还是必须使用本地错误码映射；
6. 响应对应的设备编号和发生时间取值规则；
7. 同一批历史数据重复识别时是否允许重复生成故障。

文档确认后，在 `recognition.json` 增加显式故障映射配置，或在赛方协议适配器中将响应转换成内部结构：

```ts
interface RecognizedFault {
  isFault: boolean
  errorNumber: string
  type: string
  detail?: string
}
```

识别流程为：

1. 按现有逻辑保存行为识别结果；
2. 从已确认字段解析故障结论；
3. `isFault !== true` 时结束，不产生故障；
4. 校验错误码、类型和设备编号；
5. 调用 `reportFault({ source: 'intelligence', ... })`；
6. 故障入库成功后才广播 `fault.alert`；
7. 行为记录与智能故障通过操作历史的 `relatedId` 或明确关联记录留痕，便于比赛现场追查。

行为结果保存成功但智能故障保存失败时，接口应返回明确的部分失败信息，不允许悄悄吞错；具体事务边界在取得赛方“行为结果与故障是否必须原子提交”的要求后确认。

## 前端计划

1. 故障页筛选区增加“错误来源”下拉框：全部来源、系统判定、智能判定。
2. 故障表格增加“错误来源”列，使用不同但不过度抢眼的 Tag：
   - 系统判定：蓝色或普通信息色；
   - 智能判定：紫色或警告色。
3. 页面说明改为“查询系统规则与智能判定产生的故障记录”，不再写“设备主动上报”。
4. 点击查询和重置时，来源条件与设备、类型、时间条件一起作用于列表和类型统计图。
5. 全局右上角故障提示可附带来源名称，仍只显示入库成功的故障。
6. 在没有智能故障记录时，“智能判定”筛选返回正常空状态，不隐藏该选项。

## 测试计划

### 故障报告与仓储

- `FaultReport` 缺少来源不能通过类型检查；
- 系统与智能来源分别正确写入旁表；
- 主表或旁表写入失败时事务完整回滚，不广播告警；
- 旧记录没有来源行时映射为 `system`；
- 来源筛选在 count、列表和统计中使用相同条件；
- 非法数据库来源不能伪装成已知来源，查询时记录明确异常或回退策略。

### HTTP 与前端

- 两个合法来源能够查询，非法来源返回 HTTP 400；
- options 始终返回两个固定来源；
- 页面来源列、筛选、重置、分页和空状态正确；
- 当前来源筛选同时影响列表总数和故障类型统计；
- HTTP 响应拦截器继续打印来源参数、请求头、URL、状态码和响应。

### 智能判定（取得协议后）

- 明确故障才调用一次 `reportFault(source: 'intelligence')`；
- 正常、未知、缺字段和接口失败均不写故障；
- 多故障、重复识别和部分失败按赛方确认规则测试；
- 智能判定不能绕过现有安全优先级直接控制设备。

## 验收步骤

1. 执行新迁移并确认不改变 `t_error_msg` 表结构。
2. 触发一个现有本地故障，页面显示“系统判定”。
3. 查询旧故障记录，同样显示“系统判定”。
4. 分别使用全部来源、系统判定、智能判定筛选，列表总数与统计一致。
5. 使用测试适配器模拟一条明确智能故障，确认只写一条来源为“智能判定”的记录并弹出一次警告。
6. 模拟智能识别正常结果，确认行为数据可以保存，但故障表不新增记录。
7. 运行相关测试、全量测试和 `pnpm typecheck`；按项目约定不运行生产构建。
8. 在 `1366×768` 与 `1920×1080` 下完成浏览器验证。

其中第 5、6 项属于第二阶段，必须取得赛方故障字段文档后再执行。

## 明确不做

- 不修改 `t_error_msg`、`t_error_code_mapper` 的既有字段和含义。
- 不使用 `type`、错误信息前缀或错误码前缀冒充来源字段。
- 未取得赛方字段定义前，不实现智能故障解析和入库。
- 不让智能判定直接开启、关闭设备或解除安全锁定。
- 不新增故障确认、处理状态、删除或批量操作。
