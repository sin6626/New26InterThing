# 第六里程碑：手动控制与操作日志闭环

[返回重构计划目录](../重构计划.md)

### 目标

建立“页面提交人工操作意图 → 后端读取动态指令配置并校验 → 生成兼容设备协议的 MQTT 报文 → Broker 确认发布 → 保存设备期望值与操作日志 → 页面查询结果”的闭环。本里程碑只负责人工控制的可靠传输和审计，不提前实现自动水循环、PID 或持续安全保护。

### 已确认兼容契约

- 指令定义来自现有 `t_direct_config`，不写死 `config_id`、控件类型、topic 或设备 payload。
- 比赛系统最多只有一台设备，当前期望值统一写入 `t_direct_global`；设备编号只用于 MQTT 报文和操作日志。
- 只有 `pump`、`heater` 两个设备运行指令会生成设备报文；`master` 只保存后端自动模式状态。设备报文由 `publish_topic`、`payload_template`、`value_map` 动态生成，没有自定义模板时兼容旧的 `device/direct` JSON 格式。
- MQTT 发布使用 QoS 1、禁止 retain、禁止断线缓存和恢复后补发，避免旧的开启指令在设备重连后执行。
- MQTT 发布成功只表示 Broker 已确认接收，不冒充设备已经执行；本项目目前没有明确的设备 ACK 协议。
- 设备本地操作仍可通过 `device/direct` 上报 `{ d_no, config_id, value }`，后端更新 `t_direct_global` 并记录为“设备端上报”。
- 操作历史继续使用 `t_direct_history`，不创建新表、不修改字段或索引。
- `contest_admin` 继续负责指令定义和协议模板，本项目不提供通用协议编辑器。

### 安全过渡边界

- 前端永远不能直接发布 MQTT，也不能自行决定某条指令是否安全。
- 后端统一接口同时服务当前人工操作和后续自动控制、安全保护，优先级始终为：安全关闭 > 人工关闭 > 人工开启 > 自动开启。
- 本里程碑允许水泵人工开启和关闭；所有执行器关闭指令始终允许进入下发流程。
- 在第八里程碑的传感器新鲜度、流量和泵状态保护完成前，后端拒绝人工开启加热，并返回明确中文原因；不能只在前端禁用按钮。
- `master=on` 所代表的自动运行和自动状态机留到第七里程碑；本阶段不通过普通配置更新偷偷启动自动控制。
- 目标温度、PID、超时和安全阈值等控制参数只负责校验和保存，供后续状态机使用；即使数据库残留了 `publish_topic`，也不发送 MQTT。

### 后端模块与深接口

1. `modules/control` 集中维护指令读取、值校验、协议适配、发布协调和设备端回报处理。
2. 页面只调用一个人工指令接口：
   - `POST /api/controls/commands`
   - 请求体只包含 `deviceNumber`、`configId` 和 `value`。
   - 后端重新读取 `t_direct_config`，不信任前端提交的名称、topic、模板、范围或控件类型。
3. `command.adapter.ts` 隐藏协议复杂度：
   - 解析 JSON `payload_template` 和 `value_map`。
   - 支持 `d_no`、`config_id`、`topic`、`value`、`mapped_value` 占位值。
   - 模板、映射或发布 topic 非法时停止下发并返回可操作的中文错误。
4. `command.publisher.ts` 提供单次发布接口：
   - 检查 MQTT 当前连接状态。
   - QoS 1 单次发布并受超时控制。
   - 断线或超时立即失败，不重试、不排队。
5. `control.service.ts` 固定执行顺序：读取配置与旧值 → 规范化并校验 → 安全过渡审查 → 构造报文 → MQTT 发布 → 事务保存期望值和成功日志。
6. MQTT 发布失败时不修改 `t_direct_global`，但写入 `result=failed` 的操作日志；数据库提交失败发生在发布之后时返回“设备指令可能已发布但状态保存失败”，不伪装成普通失败。
7. 新增 `device/direct` 入站解析器；应用自身发布到同一 topic 时使用短期报文指纹过滤回环，避免把自己发出的消息误记为设备端上报。
8. 时间同步作为独立人工动作：`POST /api/controls/time-sync`，由后端生成 `device/updateTime` 报文并写操作日志，不让前端拼设备时间协议。

### HTTP 接口

- `GET /api/controls/:deviceNumber`
  - 返回当前设备的有效指令配置、显示条件、控件类型、允许范围、选项和有效值。
  - 不向前端返回 `payload_template`、`value_map` 等设备协议实现细节。
- `POST /api/controls/commands`
  - 提交单设备人工操作意图。
  - 成功返回配置编号、规范化后的期望值和 `published` 状态。
- `POST /api/controls/time-sync`
  - 提交设备编号和可选时间；为空时由后端使用当前本地时间。
- `GET /api/operation-logs/options`
  - 返回数据库中已有设备、指令类型和结果筛选项。
- `GET /api/operation-logs`
  - 按设备、指令类型、发布结果、开始时间和结束时间分页查询。
  - 按 `operate_time desc, id desc` 排序。

所有接口使用现有统一响应结构；参数错误返回 HTTP 400，配置不存在返回 HTTP 404，MQTT 未连接或发布失败返回 HTTP 503，数据库异常返回 HTTP 500。

### 共享类型

- `ControlField`：配置编号、父配置关系、显示条件、名称、控件类型、范围、选项和当前有效值。
- `ControlSnapshot`：设备编号和动态控制树。
- `ControlCommandIntent`：设备编号、配置编号和页面原始值。
- `ControlCommandResult`：配置编号、规范化值和发布结果；不包含虚假的设备执行状态。
- `OperationLogItem`：记录编号、时间、设备、配置编号、指令名称、类型、旧值、新值、结果、方向和备注。
- `OperationLogQuery`、`PaginatedOperationLogs` 与 `OperationLogOptions`。

类型继续按业务文件分类放入 `packages/shared/src`，不把所有类型重新堆回 `index.ts`。

### 前端页面

1. 启用侧栏“指令控制”与“操作日志”，路由分别为 `/controls` 和 `/operation-logs`。
2. 指令页默认选择第一台设备，通过后端返回的父子关系和显示条件动态展示配置。
3. `f_type` 只映射为现有 Element Plus 控件；未知类型显示“暂不支持的控件类型”，不猜输入方式。
4. 修改后直接提交，不显示二次确认框；执行期间锁定当前控件，防止重复提交，成功后显示“修改成功”。
5. 成功后重新读取后端快照；失败时恢复后端值并显示明确原因，不能让本地开关保持虚假成功状态。
6. 加热开启在本阶段显示为不可执行并说明等待安全保护里程碑；加热关闭保持可用。
7. 操作日志页展示操作时间、方向、设备、指令名称、旧值、新值、结果和备注，支持筛选、重置与分页。
8. 操作日志只通过 HTTP 主动查询，不通过 WebSocket 自动插入，避免分页和筛选顺序被实时消息打乱。
9. 所有 HTTP 请求继续由统一拦截器打印方法、URL、请求头、参数、状态码和响应。

### 测试 seam

- 协议 seam：默认 `device/direct` 报文、自定义 topic、模板替换、值映射和非法 JSON 配置。
- 值校验 seam：开关、数字范围、单选/复选选项、未知控件类型和父配置显示条件。
- 发布 seam：QoS 1、未连接、超时、断线、禁止重试和禁止离线补发。
- 协调 seam：发布成功后保存值与成功日志；发布失败不改值并写失败日志；加热开启被后端拦截。
- 回报 seam：合法设备上报更新值并写一次日志；缺少字段、未知配置和自身 MQTT 回环均不写库。
- 仓储 seam：动态控制快照、全局单设备状态、操作日志筛选、分页和稳定排序。
- HTTP seam：成功、参数错误、配置不存在、MQTT 失败和数据库异常使用约定状态码。

### 验收场景

1. 指令页首次进入读取真实 `t_direct_config`，当前数据库中的水泵、加热和控制参数无需写死 ID 即可显示。
2. 点击水泵开启或关闭后只发布一次正确的 `command` 自定义报文，成功后页面值与 `t_direct_global` 一致并显示“修改成功”。
3. MQTT 断开时下发立即失败，不修改期望值；操作日志记录失败原因，Broker 恢复后不会补发旧开启命令。
4. 人工开启加热在安全保护完成前被后端拒绝，人工关闭加热仍可执行。
5. 设备向 `device/direct` 上报本地变化后更新数据库并记录“设备端上报”；应用自身报文不会产生重复日志。
6. 操作日志页可看到成功与失败记录，并能按设备、类型、结果和时间筛选。
7. `1366×768` 与 `1920×1080` 下控制树和日志表格无横向溢出。
8. 运行相关测试、完整测试与 `pnpm typecheck`；按约定不运行生产构建。

### 明确不做

- 不实现自动水循环启动、冷却状态机、PID、累计量或运行状态面板，这些属于第七里程碑。
- 不实现持续超温、超压、失流、干烧和传感器超时保护，这些属于第八里程碑。
- 不把 Broker 的 PUBACK 表述为设备已经执行，不猜测不存在的设备 ACK 协议。
- 不恢复旧项目的双发、无限重试、离线缓存或先改数据库后发布的行为。
- 不提供多设备控制模型；比赛系统最多只有一台设备，`t_direct_global` 即该设备的当前控制状态。
- 不修改 `t_direct`、`t_direct_config`、`t_direct_global` 或 `t_direct_history` 的表结构。
