# 第九里程碑：设备在线、数据分流与水力联合诊断

[返回重构计划目录](../重构计划.md)

### 实施结果（2026-09-14）

- MQTT `device/sensor` 报文中的 `online` 已按设备协议规范化：数字或字符串 `0` 表示正常联网实时数据，`1` 表示断网补发数据。
- 两类数据都完整写入既有 `t_sensor_data.online`；补发数据只进入历史，不刷新设备在线时间，不广播实时传感器消息，也不驱动累计水量、自动控制、安全保护或水力诊断。
- 新增设备在线服务。每次收到有效实时报文立即记录服务端 `lastSeen` 并广播在线状态；超过数据库配置 `device_offline_timeout` 后广播离线状态，并以既有 `E002/type=2` 写入一次通信异常记录；重新收到实时数据后恢复在线并开始新的离线周期。
- 新增水力联合诊断深模块，读取 `min_safe_flow`、`min_operating_pressure`、`max_safe_pressure` 和 `pressure_flow_diagnosis_confirm_time`，不新增数据库字段。
- 已实现后台配置的四个诊断编码：`HYDRAULIC_BLOCKAGE`、`HYDRAULIC_PUMP_ABNORMAL`、`HYDRAULIC_SENSOR_ANOMALY`、`HYDRAULIC_LEAK_OR_BURST`；诊断首次成立时复用 `FaultReporter` 入库并广播，恢复正常后允许下一次重新上报。
- 实时监控页展示 MQTT、WebSocket、设备在线状态、数据类型、最新时间和当前水力诊断；历史数据页用标签展示“正常联网 (0)”与“断网补发 (1)”。

### 数据分流规则

1. `online=0`：落库、刷新设备在线时间、广播实时数据、推进累计水量、自动控制、安全保护和水力诊断。
2. `online=1`：只落库供历史查询与智能识别使用，绝不参与当前控制决策。
3. 为兼容旧设备，缺少 `online` 时按实时数据处理；除 `1` 外的值均规范为实时数据。
4. 在线状态使用服务端收包时间，不能使用补发报文中的历史采集时间。

### 水力诊断规则

- 停泵、自动建流期或压力/流量无效时免检。
- 压力达到 `max_safe_pressure` 且流量低于 `min_safe_flow`：立即判断 `HYDRAULIC_BLOCKAGE`。
- 压力低于 `min_operating_pressure` 且流量低于 `min_safe_flow`：持续达到确认时间后判断 `HYDRAULIC_PUMP_ABNORMAL`。
- 压力处于参考最低压力与最大安全压力之间、流量低于最低流量：持续达到确认时间后判断 `HYDRAULIC_SENSOR_ANOMALY`。
- 最近稳定样本中压力和流量同时下降至少 35%，且绝对压降至少 20 kPa、流量下降至少 0.3 L/min：立即判断 `HYDRAULIC_LEAK_OR_BURST`。
- 诊断负责解释水力根因；第八里程碑安全门仍负责关热、停泵和故障锁定，不能被诊断模块绕过。

### 范围边界

- 第五里程碑已有的现场 HTTP 智能识别链路保持不变。
- 未取得新的赛方接口文档前，不增加或猜测新的外部智能判定字段。
- 不修改现有数据库表结构、MQTT Topic 或设备上下行格式。

### 验收

- 消息解析与实时/补发分流通过单元测试。
- 设备上线、超时离线、单周期只报告一次及重新上线通过可注入时钟测试。
- 四类水力诊断的立即判定、延时确认与骤降窗口通过单元测试。
- 后端、前端与共享类型检查通过；按项目约定未执行生产构建。
