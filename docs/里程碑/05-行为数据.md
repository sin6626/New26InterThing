# 第五里程碑：行为数据闭环

[返回重构计划目录](../重构计划.md)

### 目标

迁移设备行为数据的完整展示链路，打通“设备 MQTT 上报 → 动态字段映射 → 现有行为表入库 → WebSocket 实时推送 → 行为数据页面实时展示与历史查询”。本里程碑只忠实保存和展示设备已经给出的行为判定结果，不负责调用赛方智能判定服务，也不根据传感器数据自行生成行为结论。

### 为什么第五里程碑做这个

- 当前导航中“监控中心”只剩行为数据尚未启用，完成后监控类页面形成完整闭环。
- 行为实时与历史功能共用 `device/behavior`、`t_behavior_field_mapper` 和 `t_behavior_data`，应作为一个纵向模块迁移，避免重复建设映射、查询和图表逻辑。
- 指令控制会直接改变设备状态，并与操作日志、水循环、安全保护的优先级相互影响；在展示型模块完成后再单独规划更安全。
- 赛方智能判定接口文档尚未取得，不能猜测请求、响应或媒体字段，因此不应混入本里程碑。

### 兼容契约

- MQTT 继续使用现有 Broker，新增订阅旧协议主题 `device/behavior`。
- 行为报文必须提供 `d_no`；业务字段通过 `t_behavior_field_mapper.p_name` 与报文属性匹配，不在代码中写死 `field1` 至 `field10` 的业务含义。
- 行为记录继续写入 `t_behavior_data`，字段定义继续读取 `t_behavior_field_mapper`；不创建表、不修改现有字段或索引。
- `c_time` 优先取报文中的 `c_time`，其次兼容 `time`，均缺失时使用服务端接收时间。
- `online` 只作为旧表中的原始展示字段保存，不用它推导设备在线状态；设备在线状态仍以现有实时遥测链路为准。
- 只有行为记录成功入库后才广播 `behavior.realtime`，避免前端展示数据库中不存在的数据。
- 映射表中的 `visible` 决定页面是否展示字段；`type` 只按数据库已有含义处理，不扩展或猜测新枚举。

### 后端交付

1. 新建独立 `modules/behavior`，集中放置行为报文解析、字段映射、入库、实时读取、历史查询和 HTTP 路由。
2. 扩展现有 MQTT 基础设施，同时接收 `device/sensor` 与 `device/behavior`，按 Topic 明确分派；两个模块不得共享含混的通用数据保存函数。
3. 每条行为消息读取当前字段映射，只允许目标列为 `field1` 至 `field10`；拒绝未知数据库列名，防止映射配置被拼入任意 SQL。
4. 校验 JSON、设备编号、映射字段和值；单条非法消息只记录明确错误，不使 MQTT 客户端退出，也不影响后续消息。
5. 使用参数化 SQL 写入 `t_behavior_data`；成功后广播共享消息 `behavior.realtime`，内容使用业务字段名而不是数据库列名。
6. 提供页面专用接口：
   - `GET /api/behaviors/options`：返回设备选项和当前可见字段定义。
   - `GET /api/behaviors/latest`：返回指定设备最新一条行为记录；未指定设备时返回各设备最新记录。
   - `GET /api/behaviors`：按设备、开始时间、结束时间分页查询，按 `c_time`、`id` 倒序。
   - `GET /api/behaviors/trend`：按相同筛选条件返回可绘图数值字段的时间序列，限制最大点数。
7. 参数错误返回 HTTP 400；映射缺失、无可保存字段和仓储异常进入统一错误处理，不广播实时消息。

### 共享类型与消息

- `BehaviorField`：字段键、显示名称、单位、数据类型和是否可见。
- `BehaviorItem`：记录编号、设备编号、动态业务字段、原始在线字段和发生时间。
- `BehaviorOptions`：设备编号和字段定义。
- `PaginatedBehaviors`：行为历史分页结果。
- `BehaviorTrend`：时间轴与各数值字段序列。
- `BehaviorRealtimeMessage`：`{ type: 'behavior.realtime', data: BehaviorItem }`。

前端只使用共享类型中的业务字段，不直接接触 `field1` 至 `field10` 或其他数据库列名。

### 前端交付

1. 启用侧栏“行为数据”，路由使用 `/behaviors`。
2. 在 `features/behavior` 中集中维护 API、WebSocket 消息处理、筛选、分页、加载和错误状态，页面只组合 UI。
3. 页面上半区展示各设备最新行为结果；选择设备后展示该设备的最新动态字段和最近趋势。
4. 页面下半区提供设备、时间范围筛选、动态列历史表格、分页，以及可见数值字段趋势图。
5. 收到 `behavior.realtime` 后更新对应设备的最新结果；若当前正在查看同一设备，则增量更新实时区和趋势窗口。历史分页列表不硬插数据，用户点击查询时再按数据库结果刷新。
6. WebSocket 重连后主动补拉最新数据与当前趋势，弥补断线期间遗漏的消息。
7. 映射中的普通文本和数值字段直接展示；图片、视频等媒体字段只有在字段含义和返回格式明确时才接入预览，否则保留为文本值并在实施前向用户确认，不猜 URL 或数据结构。
8. 查询失败时清空对应旧数据并显示明确错误；无记录或无可绘图数值字段时显示空状态。
9. HTTP 请求继续由现有响应拦截器输出方法、URL、请求头、参数、状态码和响应的结构化 JSON 日志。

### 测试 seam

- 解析 seam：合法 JSON、非法 JSON、缺失 `d_no`、时间优先级和服务端时间回退。
- 映射 seam：物理字段到数据库字段再到业务字段的双向映射、`visible` 过滤、非法目标列拒绝、缺失字段保存为 `null`。
- 处理 seam：入库成功后只广播一次，解析、映射或入库失败时不广播。
- 仓储 seam：各设备最新记录、单设备最新记录、设备与时间筛选、分页排序和趋势点数限制。
- HTTP seam：四个接口返回统一响应；非法页码、时间范围和趋势点数返回 400；仓储异常返回 500。
- WebSocket seam：`behavior.realtime` 使用共享消息结构，并保持现有 `sensor.realtime`、`fault.alert` 和 `system.status` 行为不变。
- 前端执行 TypeScript 检查和真实浏览器流程验证；按用户约定，阶段开发期间不执行生产构建。

### 验收场景

1. 行为页首次打开能读取真实字段映射和已有 `t_behavior_data`，动态字段名称、单位、可见性正确。
2. 向 `device/behavior` 发布一条符合现有映射的消息后，只入库一次；对应设备的实时行为结果和趋势无需刷新即可更新。
3. 切换设备时不会串数据；WebSocket 断开重连后能通过 HTTP 补回最新状态。
4. 设备和时间筛选下，历史总数、分页数据与趋势使用相同条件，顺序稳定。
5. 非法 JSON、缺失设备编号、非法映射列和数据库写入失败不会广播虚假数据，也不会使服务退出。
6. 映射表修改显示名称、单位或可见性后，重载页面即可按新配置展示，无需修改代码。
7. 在 `1366×768` 与 `1920×1080` 下页面无横向溢出，动态字段较多时仍可正常查看表格和图表。
8. 相关自动化测试、完整测试与 `pnpm typecheck` 通过；生产构建留到全部里程碑开发完成后由用户统一执行。

### 明确不做

- 不调用或模拟赛方智能判定接口，不猜测请求模板、响应字段或媒体格式。
- 不从传感器历史页选择数据并发起识别；该流程等赛方接口文档明确后单独规划。
- 不在本地生成、修正或解释行为判定结果，只保存设备已经上报的内容。
- 不实现指令控制、操作日志、水循环、PID、安全保护或故障诊断。
- 不修改 `t_behavior_field_mapper`；映射配置继续由现有独立后台维护。
- 不用 `online` 字段替代现有设备在线状态判断。
- 不为普通展示组件堆单元测试，不运行阶段性生产构建。
