# 第八里程碑：持续安全保护、故障锁定与人工复位

[返回重构计划目录](../重构计划.md)

### 目标

在第七里程碑自动控制骨架上增加后端唯一的持续安全守卫，形成“实时读数/定时巡检 → 确定性规则判定 → 立即撤销危险动作 → 必要时停泵 → 故障锁定 → 故障记录与实时警告 → 人工确认复位”的闭环，并在验收完成后替换当前无条件禁止 `heater=on` 的临时安全门。

安全保护覆盖自动模式、人工模式、停止和冷却状态，不能只在 PID 运行时生效。任何页面、HTTP 调用或 MQTT 发布结果都不能绕过后端安全判定。

### 当前尚未完成的能力

- 自动状态机还没有正式 `FAULT` 状态、结构化故障码、故障锁定和人工复位。
- 当前 `heater=on` 被 `control.service` 无条件返回 `HEATER_SAFETY_BLOCKED`；它尚未根据实际水泵、流量、压力、温度和数据新鲜度动态放行。
- `AutomationReading` 只有出口温度和流量，尚未包含入口温度、压力以及各字段独立更新时间，无法完成超压、探头装反和分传感器超时判断。
- 建流超时、运行失流、超温、超压和指令发布失败目前没有统一进入故障锁定，也没有调用第四里程碑的 `reportFault()`。
- `fault-reporter.ts` 已存在但尚未在 `main.ts` 组装，自动控制不能写入 `t_error_msg` 或广播 `fault.alert`。
- 当前安全错误映射要求调用方同时给出 `e_no + type`，但数据库注释与旧项目使用的 `3/6` 类型码不一致；安全模块不能猜类型。
- 页面只能展示正常状态机和最近动作，没有故障码、故障原因、保护动作、传感器新鲜度和复位入口。

### 范围边界

本里程碑实现能够直接由传感器值、执行器反馈、配置阈值和时间窗口确定的保护：

1. 启动建流超时。
2. 运行或冷却期间持续低流量。
3. 水泵人工开启后建流失败/疑似空转。
4. 超压。
5. 超温。
6. 流量、压力、温度传感器超时或无效。
7. 进出口温度传感器疑似装反。
8. 加热开启后在有效加热时间内出口温度无明显上升。
9. 控制配置在运行中失效。
10. MQTT 指令发布失败，尤其是安全关闭失败。

本里程碑不实现水力联合诊断，不根据压力与流量组合推断“堵塞、泄漏、管路脱落、流量计卡阻”等根因；这些属于第九里程碑的故障诊断。安全模块可以因超压或低流立即停机，但不猜测故障根因。

### 安全深模块

新增 `modules/safety`，其 interface 只接收规范化事实并返回保护决定，不直接访问 MySQL、MQTT、Express 或 WebSocket：

```ts
interface SafetySupervisor {
  handleReading(reading: SafetyReading, context: SafetyContext): SafetyDecision
  tick(now: number, context: SafetyContext): SafetyDecision
  authorize(action: SafetyAction, context: SafetyContext): SafetyAuthorization
  canReset(context: SafetyContext): SafetyAuthorization
  reset(): void
  getSnapshot(): SafetySnapshot
}
```

- `handleReading()` 更新每个传感器的独立有效时间，推进低流、装反和无温升确认窗口，并返回当前最高优先级保护决定。
- `tick()` 使用可注入单调时钟检查没有新 MQTT 消息时的传感器超时、确认时间和故障散热倒计时。
- `authorize()` 是人工与自动动作共用的唯一安全门；关闭动作始终允许，开启加热和开启水泵分别校验所需条件。
- `canReset()` 只判断复位条件，不执行 MQTT 或数据库操作。
- `SafetyDecision` 只描述 `faultCode`、中文事实详情、是否立即关热、是否停泵及冷却策略；具体动作、故障锁定、入库和广播由自动控制引擎协调。
- 所有安全决策继续进入第七里程碑的单设备串行队列，避免读数、巡检、人工操作和复位互相覆盖。

建议内部文件：

- `safety-supervisor.ts`：规则优先级、确认窗口和故障锁存事实。
- `safety.types.ts`：读数、上下文、决定、授权和快照类型。
- `sensor-freshness.ts`：每字段有效性、零值观察和超时判定。
- `heating-watch.ts`：装反与有效加热时间内无温升观察。
- 不为每条简单 `if` 建一个文件；规则仍通过一个小 interface 对外提供完整能力。

### 规范化实时读数

在实时消息成功保存后只规范化一次，再把同一份读数传给累计水量、自动状态机和安全模块：

- `tempIn`：优先 `temp_in`，兼容旧字段 `field3`。
- `tempOut`：优先 `temp_out`，兼容旧字段必须以数据库传感器定义和旧设备报文再次核对后确定；当前代码使用 `field4`，旧控制代码使用 `field2`，实施前必须先确认，不能猜。
- `flowRate`：优先 `flow_rate`，兼容 `field5`。
- `pressure`：优先 `pressure`，兼容字段同样以数据库定义为准；不能与出口温度字段复用。
- `actualPump`、`actualHeater` 只认设备报文 `water_Y2`、`heat_Y1`，PUBACK 不作为实际状态。
- 缺失字段不刷新该字段时间；空字符串、非有限数字和协议确认的断线值进入无效观察。
- 服务端接收时间用于安全超时和确认窗口，设备上报时间只用于展示，避免设备时钟漂移破坏保护。

`temp_out/pressure` 的旧字段对应关系存在现有代码冲突，这是实施第八里程碑前必须解决的协议确认项。未确认前可以先完成使用语义字段名的纯规则和测试，但不能接通生产保护动作。

### 保护优先级与动作

优先级继续遵守：安全保护/紧急停机 > 人工停机 > 人工临时控制 > 自动控制。同一轮出现多个问题时只锁定最高危险决定，同时把其他事实附加到详情：

1. 超压、流量/压力传感器失效、冷却失流：立即禁止加热，先尝试关热，再停泵，进入 `FAULT`。
2. 超温：立即禁止并关闭加热；只有实际水泵开启、流量安全、压力安全且相关传感器有效时才保留水泵运行 `cooling_delay`，否则立即停泵。
3. 加热中失流：第一次观察即撤销加热期望并下发关热；持续达到 `low_flow_confirm_time` 后锁定故障并停泵。
4. 非加热运行中的持续低流量：确认后关热、停泵并锁定故障。
5. 温度传感器超时、装反或无温升：立即禁止并关闭加热；水力条件安全时允许限时循环散热，随后停泵并保持 `FAULT`。
6. 建流超时或人工水泵空转：禁止加热、关闭水泵并锁定故障。
7. 开启指令发布失败：不离线排队、不重试旧的开启动作，进入故障并执行安全关闭。
8. 安全关闭失败：仍保持 `FAULT`，在实际执行器仍开启时允许调度器按一秒节流重发当前关闭动作；永不重发开启动作，也不能阻止继续尝试关闭另一个执行器。

故障状态必须锁存。后续读数恢复正常只能更新“当前条件已安全”，不能自动清除故障或重新开启设备。

### 确定性规则

#### 开启加热授权

只有同时满足以下条件才允许人工或自动 `heater=on`：

- 不在故障锁定、停止中或保护动作进行中。
- 配置合法，最近读数完整且各相关字段未超过 `data_timeout`。
- 实际水泵为 `on`；仅有期望水泵开启或 MQTT 发布成功不够。
- 流量 `>= min_safe_flow`。
- 压力 `< max_safe_pressure`。
- 入口和出口温度均大于协议确认的断线值，且最高温度 `< max_safe_temperature`。
- 没有处于低流、装反、无温升或其他保护的确认观察中。

所有关闭指令始终允许。第八里程碑完成后删除无条件加热禁用，只保留这一动态安全门。

#### 超压与超温

- 实际水泵开启且压力 `>= max_safe_pressure` 时触发 `OVER_PRESSURE`，关热并停泵。
- 任一有效水温 `>= max_safe_temperature` 时触发 `OVER_TEMPERATURE`，立即关热；是否保留水泵散热按当前水力条件决定。
- 边界采用包含比较；安全阈值恰好达到上限即视为不安全。

#### 建流、失流与人工水泵空转

- 自动 `BUILDING_FLOW` 超过 `build_flow_timeout` 仍未达到安全流量，升级为 `BUILD_FLOW_TIMEOUT` 并锁定，而不是回到普通 `STOPPED`。
- 实际或期望水泵由人工开启时建立独立建流观察；超时仍未达到安全流量触发 `PUMP_IDLING` 并关泵。
- `RUNNING` 中流量低于阈值时立即关热，持续达到 `low_flow_confirm_time` 后触发 `LOW_FLOW`。
- `COOLING/FAULT` 散热期间流量低于阈值不等待确认，立即停泵，防止水泵空转。
- 压力只作为安全阈值，不在本里程碑据此推断具体水力根因。

#### 传感器有效性与超时

- 分别跟踪 `tempIn`、`tempOut`、`flowRate`、`pressure` 的最后有效接收时间，不能用“整包最后更新时间”代替。
- 活动控制包括状态机非停止、实际或期望水泵开启、实际或期望加热开启；仅在活动控制时把超时升级为故障。
- 流量失效触发 `SENSOR_FLOW_TIMEOUT`，压力失效触发 `SENSOR_PRESSURE_TIMEOUT`，两者都停止水泵。
- 温度失效触发 `SENSOR_TEMPERATURE_TIMEOUT`，先关热；水力安全时完成限时散热后停泵。
- 温度零值始终按无效观察；流量和压力零值在停机时可以是真实值，在活动控制时同时参与低流/空转与断线确认。实现必须用测试固定二者优先关系，避免把真实零流误报成通信超时。

#### 温度探头装反

- 仅在实际水泵开启、流量安全、实际加热开启且两个温度字段有效时观察。
- 当入口温度持续高于出口温度超过已确认容差并达到 `temp_reversed_confirm_time` 时触发 `TEMP_SENSOR_REVERSED`。
- 条件中断时清空连续确认计时；故障确认后关热并按安全水力条件散热。
- 容差不能沿用旧代码中未配置的 `0.1℃` 魔法值。实施前优先复用已有明确配置；若无可用配置，需要用户确认是否新增后台配置，不能擅自写死。

#### 加热后无温升

- 只累计“实际加热开启、实际水泵开启、流量安全、温度有效”期间的有效加热时间。
- 累计达到 `dry_heating_timeout` 后，出口温升仍小于 `dry_heating_temp_diff` 时触发 `DRY_HEATING_NO_TEMP_RISE`。
- 加热关闭、失流、读数无效或状态离开运行时暂停累计；长时间停用或复位时清空基线。
- 该规则只报告“有效加热时间内无温升”，不在本里程碑推断加热器损坏、探头故障或真正干烧的根因。

### 故障状态与复位

`AutomationState` 增加 `fault`。故障快照至少包含：

- `faultCode`、事实详情、发生时间。
- 是否已写入故障表、最近入库错误。
- 保护要求的关热/停泵策略与当前执行结果。
- 哪些传感器超时或无效。
- 是否允许复位及不允许复位的中文原因。

进入故障时先同步锁存状态和撤销所有开启期望，再串行执行保护动作。数据库映射、故障入库或 WebSocket 广播失败只能记录错误，不能阻止关热、停泵或故障锁定。

人工复位必须满足：

- 当前确实处于 `FAULT`，且没有并发的新故障决定。
- 控制配置合法。
- 必需传感器数据完整、新鲜且不再达到超温/超压阈值。
- 实际与期望加热均为关闭；复位流程会强制再发布一次关热和关泵。
- 两次关闭成功后重新读取安全事实，期间任何新故障或 generation 变化都使复位失败。

复位成功只进入 `STOPPED` 并清理确认计时，不自动恢复 `master=on`，不自动重新开泵或加热。

### 故障记录与映射

- 在 `main.ts` 创建并注入第四里程碑的 `FaultReporter`，所有本地安全规则只能通过它写 `t_error_msg` 和广播 `fault.alert`。
- 为本地规则增加按 `e_no` 查询完整映射的仓储方法，返回数据库中的 `e_no/type/e_msg`；不能由安全模块硬编码 `type`。
- 若同一 `e_no` 没有映射或存在多个不同 `type`，保存内部故障码、明确中文事实详情和 `type=null`，同时记录映射问题；不猜 `1/2/3/6`。
- 不自动创建表、不修改表结构，也不在应用启动时写入或覆盖 `t_error_code_mapper`；映射继续由 `contest_admin` 维护。
- 同一故障锁定周期只入库并广播一次；调度器重复执行安全关闭不能重复制造故障记录。

建议使用的内部故障码沿用已有业务语义：`CONTROL_CONFIG_INVALID`、`BUILD_FLOW_TIMEOUT`、`COMMAND_PUBLISH_FAILED`、`LOW_FLOW`、`PUMP_IDLING`、`OVER_PRESSURE`、`OVER_TEMPERATURE`、`SENSOR_FLOW_TIMEOUT`、`SENSOR_PRESSURE_TIMEOUT`、`SENSOR_TEMPERATURE_TIMEOUT`、`TEMP_SENSOR_REVERSED`、`DRY_HEATING_NO_TEMP_RISE`。实施前只读检查后台映射覆盖情况，不补写映射。

### 与自动控制和人工控制集成

- `AutomationEngine` 继续是单设备运行状态的唯一所有者；安全 supervisor 作为内部模块注入，不建立第二套状态机。
- `handleReading()` 在推进建流或温控前先处理安全决定；一旦决定关热，本轮不得继续执行 PID 开启。
- `tick()` 在加载新配置和推进 PID 开启前，先用最近已验证配置执行传感器超时和当前保护关闭，数据库读取延迟不能延长危险动作。
- `control.service` 对人工 `heater=on`、`pump=on` 调用与自动控制相同的 `authorize()`；人工关闭不需要授权。
- 自动模式、冷却或故障期间禁止人工开启运行指令；人工停止仍可触发关热和停泵流程。
- `master=on` 在故障锁定期间返回 HTTP 409 和具体中文原因；`master=off` 不解除故障。
- 安全关闭继续复用 `control.service` 的动态报文、MQTT 超时和操作日志，备注中标明故障码与保护原因。

### HTTP、WebSocket 与共享类型

复用 `GET /api/automation/:deviceNumber` 返回完整安全快照，并新增：

- `POST /api/automation/:deviceNumber/fault/reset`：人工确认复位；成功只返回停止状态快照。

`automation.status` 增加故障状态、故障码、原因、保护动作、传感器新鲜度和复位条件。故障成功入库后仍由既有 `fault.alert` 触发全局右上角警告，不再新增重复告警消息类型。

共享类型新增 `AutomationState='fault'`、`SafetySnapshot`、`SafetyFaultCode`、复位结果和必要的传感器状态；不向前端暴露内部计时器、队列或数据库列名。

### 前端页面

继续复用 `/controls`，不新增独立安全页面：

- 自动状态卡增加红色故障状态、故障码、中文原因和发生时间。
- 展示四类传感器的正常/无效/超时状态以及当前保护动作。
- 故障时禁用所有开启操作，但关闭操作保持可用。
- 显示“确认并复位”按钮；点击前二次确认，失败时展示后端返回的具体条件，不在前端自行判断能否复位。
- 删除“第八里程碑前不会真正开启加热”的临时提示，替换为当前安全门状态说明。
- 故障历史页面保持 HTTP 查询，不因实时警告自动篡改列表；用户主动查询后看到新记录。

### 测试 seam

- 授权 seam：手动与自动加热使用同一安全门；实际泵未开、流量不足、超压、超温、数据过期、故障锁定时拒绝，关闭始终允许。
- 状态机 seam：任意活动状态进入 `FAULT`、故障锁定不自动恢复、`master=off` 不清故障、复位成功只到 `STOPPED`。
- 优先级 seam：同轮超压与超温以停泵策略优先；安全决定阻止同轮 PID 开热。
- 低流 seam：首次失流立即关热、确认时间内不误锁、持续低流锁定、恢复后计时清零、冷却失流立即停泵。
- 建流 seam：自动建流超时与人工泵空转分别记录正确故障码并只关泵一次。
- 新鲜度 seam：每字段独立更新时间、缺失字段不刷新、非法值和零值观察、无 MQTT 时由 `tick()` 触发。
- 温度 seam：超温包含边界、装反确认与中断重置、有效加热时间累计、无温升阈值与暂停恢复。
- 指令失败 seam：开启失败不重试；关热失败仍尝试关泵；故障关闭按节流重试；旧开启动作不会在恢复连接后补发。
- 复位 seam：危险条件未解除、配置非法、数据超时、复位期间新故障、关闭发布失败均拒绝复位。
- 故障报告 seam：映射命中、映射缺失/歧义、单次入库广播、入库失败不阻断保护、同一故障不重复记录。
- HTTP/WebSocket seam：启动拒绝和复位错误返回明确 409；快照与 `automation.status` 包含相同安全字段。
- 实时集成 seam：传感器先成功入库和广播，再执行派生安全规则；安全模块失败不能吞掉原始实时消息。

测试使用可注入单调时钟和假执行器，不使用真实等待、真实 MQTT 或真实设备。安全相关测试必须覆盖阈值等号、并发 generation、动作顺序与失败补偿。

### 实施顺序

1. 确认 `temp_out`、`pressure` 的旧字段映射及装反容差来源；只读核对错误码映射覆盖。
2. 扩展规范化读数和共享安全类型，补齐每字段新鲜度。
3. 先以纯函数和假时钟实现安全 supervisor 的授权、超温、超压、低流和超时规则。
4. 将 supervisor 接入自动引擎串行队列，增加 `FAULT` 锁定、保护动作和关闭重试。
5. 接入人工控制统一授权，替换无条件加热禁用。
6. 实现装反与有效加热无温升观察。
7. 接入 `FaultReporter`、动态错误映射、单次入库和 `fault.alert`。
8. 增加复位接口和 `/controls` 故障 UI。
9. 运行相关测试、完整测试和类型检查；使用测试 MQTT 或假发布器验证动作顺序。
10. 在确认现场设备断开或用户明确授权后，才进行真实开泵/加热受控写入验收；阶段内不执行生产构建。

### 验收场景

1. 正常新鲜读数、实际水泵开启、流量/压力/温度安全时，自动与人工加热可通过统一安全门；任一条件不满足时返回具体原因且不发布。
2. 加热中出现超温、超压或首次失流时，危险开启期望同步撤销，关热动作先于其他动作。
3. 超压、流量/压力失效和冷却失流会停泵；单独超温或温度故障只在水力安全时保留限时散热。
4. 没有新 MQTT 消息时，调度器仍能按每字段 `data_timeout` 触发保护。
5. 建流失败、人工泵空转、持续低流、装反和无温升均按确认窗口触发一次故障记录和一次实时警告。
6. 故障后读数自行恢复不会自动重启；未满足复位条件时返回明确原因，复位成功只回到停止状态。
7. MQTT 发布失败不会导致旧开启动作离线补发；安全关热失败不妨碍继续关泵和锁定故障。
8. `t_error_msg` 使用后台映射的类型和中文信息；未知或歧义映射不猜类型，且入库失败不阻断停机。
9. `/controls` 首次 HTTP 快照即显示安全状态，WebSocket 后续更新无需切换路由；1366×768 与 1920×1080 无横向溢出。
10. 相关单测、完整测试、类型检查、只读数据库联调通过；按约定不执行生产构建。

### 实施前必须确认

以下信息当前资料存在冲突或缺失，不能在实现时猜测：

1. 旧设备兼容字段中，`temp_out` 和 `pressure` 分别对应哪个 `fieldN`。当前新代码把 `temp_out` 回退到 `field4`，旧控制代码把 `temp_out` 回退到 `field2`，两者冲突。
2. 温度装反判定容差是否使用固定 `0.1℃`，还是需要由 `contest_admin` 增加一条现有表内配置；未确认前不能写死。
3. 后台当前是否已为全部本地安全故障码配置唯一的 `e_no/type/e_msg` 映射；若存在同一 `e_no` 多种 `type`，需要后台明确选择规则。

### 明确不做

- 不修改任何既有数据库表结构，不自动建表或补写错误码映射。
- 不实现水力堵塞、泄漏、管路脱落、流量计异常等联合诊断。
- 不接入第九里程碑的智能判定或赛方故障诊断接口。
- 不新增设备 ACK 协议，不把 MQTT PUBACK 当作实际执行成功。
- 不自动复位、不自动恢复 `master=on`，不在故障后恢复旧开启动作。
- 不开发故障处理工单、权限、声音告警或移动端。
