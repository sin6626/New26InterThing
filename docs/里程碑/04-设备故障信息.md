# 第四里程碑：设备故障信息闭环

[返回重构计划目录](../重构计划.md)

### 目标

建立本地故障记录的统一闭环：“业务规则判断传感器数据 → 调用统一错误函数 → 中文信息映射 → 现有故障表入库 → 右上角即时警告”，并由故障页面通过 HTTP 查询历史记录。本里程碑先完成可靠的错误记录能力，不提前迁移具体水循环规则、自动停机或智能判定。

### 兼容契约

- 设备只上传 `device/sensor` 传感器数据，不会主动上报错误；后端不订阅 `device/error`。
- 后续本地判断模块统一调用 `reportFault({ deviceNumber, errorNumber, type, detail })`，不允许各模块自行写故障 SQL。
- 故障记录继续写入 `t_error_msg`，中文映射继续读取 `t_error_code_mapper`；不创建表、不修改字段或索引。
- `type` 作为设备协议原值保存和筛选，不在代码中猜测完整枚举；页面优先显示映射表或记录中的中文信息，未知值保留原始类型码。
- 故障页面与历史数据页面一致，只通过 HTTP 主动查询，不使用 WebSocket 更新列表或自动轮询；WebSocket 仅发送 `fault.alert` 供全局右上角即时提醒。

### 后端交付

1. 独立 `modules/fault` 集中放置统一错误函数、中文映射、仓储和 HTTP 路由。
2. `reportFault()` 接收设备编号、错误编号、类型、可选具体原因和时间；调用方只负责判断业务故障。
3. 使用 `e_no + type` 查询 `t_error_code_mapper`；命中时使用标准中文信息，未命中时生成包含原始编号和类型的明确文本，具体原因附加在标准信息后。
4. 只有 `t_error_msg` 写入成功后才广播 `fault.alert`；映射或入库失败时不发送虚假警告。
5. 提供页面专用接口：
   - `GET /api/faults/options`：返回设备与数据库中已有类型筛选项。
   - `GET /api/faults`：按设备、类型、开始时间、结束时间分页查询，按 `c_time`、`id` 倒序。
   - `GET /api/faults/statistics`：按与列表相同的筛选条件统计各类型数量，供页面图表使用。
6. 参数错误返回 HTTP 400，仓储异常交由统一错误处理中间件返回 HTTP 500。

### 共享类型

- `FaultItem`：记录编号、设备编号、故障编号、原始类型码、中文信息和发生时间。
- `PaginatedFaults`：故障列表分页结果。
- `FaultStatisticsItem`：类型码、显示名称和数量。
- `FaultAlertMessage`：`{ type: 'fault.alert', data: FaultItem }`，只服务全局即时警告。
前端只使用共享类型中的业务字段，不直接接触数据库列名。

### 前端交付

1. 启用侧栏“故障信息”，路由使用 `/faults`。
2. 在 `features/fault` 中集中维护 API、筛选、分页、加载与错误状态，页面只组合 UI。
3. 使用 Element Plus 提供设备、类型、时间范围筛选及分页表格，展示设备编号、故障编号、类型、故障信息和发生时间。
4. 使用 ECharts 展示当前筛选条件下的故障类型数量分布；统计使用独立接口，不根据当前分页的十几条数据计算，避免比例失真。
5. 页面首次进入、点击查询、重置筛选和切换分页时发起 HTTP 请求；不会因 MQTT 新消息自动更新。
6. 查询失败时清空旧列表与旧统计并显示明确错误；无数据时显示空状态。
7. HTTP 请求继续由现有响应拦截器打印结构化调用信息。
8. 应用布局只建立一个共享 WebSocket 连接；收到 `fault.alert` 后使用 Element Plus 在右上角显示故障设备和中文信息。

### 测试 seam

- 报告 seam：映射命中与默认文本、具体原因拼接、时间回退和单次入库。
- 通知 seam：入库成功后广播一次 `fault.alert`，映射或入库失败时不广播。
- 仓储 seam：列表与统计共用设备、类型和时间条件，分页与排序正确。
- HTTP seam：三个接口返回统一响应，非法参数返回 400，仓储异常返回 500。
- 前端执行 TypeScript 检查和真实浏览器流程验证；按用户约定，阶段开发期间不执行生产构建。

### 验收场景

1. 故障页首次打开能读取真实 `t_error_msg`，筛选、分页和类型统计正常。
2. 本地规则调用一次 `reportFault()` 后，记录只写入一次，并在右上角弹出一次警告；点击故障页面查询后能看到新记录。
3. 传入 `e_no + type` 时能使用 `t_error_code_mapper` 得到中文信息；未知映射仍能保存可理解的回退文本。
4. 设备、类型和时间筛选下，列表总数与统计使用相同条件。
5. 映射或数据库写入失败不会弹出虚假警告，也不会重复入库。
6. 在 `1366×768` 与 `1920×1080` 下页面无横向溢出。
7. 自动化测试与 `pnpm typecheck` 通过；生产构建留到全部里程碑开发完成后由用户统一执行。

### 明确不做

- 不实现水循环状态机、安全保护、故障诊断或自动下发停机指令。
- 不接入智能判定，不写入行为数据。
- 不开发确认、处理、删除、批量操作或声音告警。
- 不维护错误码映射表；该表继续由现有项目管理后台管理。
- 不迁移旧页面中写死的 1 至 6 类型名称，除非数据库映射或设备协议能够明确提供含义。
- 不实现设备心跳或在线/离线判断。
- 不为故障页面列表增加 WebSocket 更新或自动轮询。
- 不订阅设备端 `device/error`；故障只能由本地业务规则调用统一错误函数产生。

## 第四里程碑验证记录

2026-09-11 已完成：

- 使用真实 MySQL 只读验证三个 HTTP 接口，读取到 1 个设备、3 种故障类型和原有 78 条故障记录。
- 用户澄清设备不会主动上报故障后，已移除 `device/error` 订阅、解析器和处理器，MQTT 恢复为只订阅 `device/sensor`。
- 新增统一 `reportFault()`：按 `e_no + type` 映射、单次写库，成功后广播 `fault.alert`；失败不广播。
- 故障页面仍只通过 HTTP 查询列表和统计，不监听 `fault.alert` 修改页面数据；全局布局使用共享 WebSocket 在右上角弹出即时警告。
- 在 `1366×768` 与 `1920×1080` 下验证筛选、20 条分页表格和类型统计图，无横向溢出、错误覆盖层或控制台错误。
- 自动化测试覆盖统一报告函数、时间回退、中文映射与回退、单次入库、成功通知、失败不通知、筛选分页、统计、HTTP 参数和异常边界；完整测试与 TypeScript 类型检查通过。
- 按用户约定未运行生产构建。
