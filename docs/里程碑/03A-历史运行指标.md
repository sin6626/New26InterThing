# 第三里程碑补充：历史运行指标

[返回第三里程碑](./03-传感器历史数据.md)

## 目标

在现有历史数据页面增加可由 `t_sensor_data` 可靠推导的运行指标，让用户按当前设备和时间筛选条件查看：

- 水泵实际运行时长；
- 加热实际运行时长；
- 出口水温每分钟变化趋势。

本功能不把实时页的进程内累计值直接搬到历史页。历史页展示的是“当前查询范围内”的统计结果，服务重启不影响历史查询。

## 数据边界与统计口径

### 数据来源

只读取现有表和已确认字段映射，不修改数据库结构：

| 指标 | 协议字段 | 数据库字段 | 口径 |
| --- | --- | --- | --- |
| 水泵运行时长 | `water_Y2` | `field7` | 只认设备实际反馈为 `1`/`on` 的有效相邻采样间隔 |
| 加热运行时长 | `heat_Y1` | `field6` | 只认设备实际反馈为 `1`/`on` 的有效相邻采样间隔 |
| 出口水温变化 | `temp_out` | `field2` | 使用有效出口水温采样计算滚动每分钟变化速度 |

数据库列必须由 `t_sensor_field_mapper` 校验后使用，不能在 HTTP 参数中接收任意列名。

### 运行时长

1. 按设备和 `c_time`、`id` 正序处理查询范围内的数据。
2. 算法与实时 `operational-metrics` 保持一致：当前采样反馈为开启时，才把它与上一条采样的时间差计入对应运行时长。
3. 时间差必须大于 `0`，且不超过当前配置的 `data_timeout`；断线、长时间无报文和时间倒退均不补算。
4. 查询开始时间之前额外读取同设备最近一条记录，只用于判断范围内首条记录的有效时间差；累计区间必须裁剪到用户选择的开始时间，不能把范围外时间算入结果。
5. 查询结束时间之后不外推运行状态；最后一条记录之后的时间不计入。
6. `0`/`off` 视为关闭，缺失值和非法值视为 `unknown`，均不累计。
7. 断网补发数据按其设备采集时间 `c_time` 排序参与计算，但同一时间的重复或非递增记录不重复累计。

因此，历史运行时长是查询区间统计，不等同于实时页“本次服务进程启动以来”的累计时长。

### 出口水温每分钟变化

1. 复用或抽取实时指标中的纯计算规则，避免实时页和历史页出现两个公式。
2. 对每条有效 `temp_out` 采样，在最近 60 秒窗口中取最早有效点与当前点：`(当前温度 - 最早点温度) / 实际秒数 × 60`。
3. 样本跨度不足 5 秒时返回空值，非法数值不参与计算。
4. 页面趋势按自然分钟归并，每分钟保留该分钟最后一个有效计算结果；正数表示升温，负数表示降温，单位为 `℃/min`。
5. 为计算查询范围起点的滚动窗口，后端可额外读取开始时间之前最多 60 秒的温度样本，但只返回查询范围内的分钟点。

## 后端计划

### 共享类型

在 `packages/shared/src/sensor-history.ts` 增加：

- `SensorHistoryOperationalMetrics`：设备编号、查询起止时间、水泵秒数、加热秒数、温度变化时间轴与序列；
- 明确空数据返回 `0` 秒和空趋势，不使用 `null` 代表运行时长；
- 温度变化点允许 `null`，用于表达该分钟样本不足。

### 仓储与领域计算

1. 在 `sensor-history` 模块增加独立运行指标查询能力，复用现有设备、开始时间和结束时间筛选。
2. 把运行时长和温度变化公式提取为可单测的纯函数；实时 `operational-metrics` 与历史计算共用状态归一化和温度速率公式。
3. 仓储只负责读取必要字段和时间边界样本，领域函数负责排序、去重、超时判断、区间裁剪和按分钟归并。
4. 查询只需要一个设备。当前页面虽隐藏设备选择器，但接口要求 `deviceNumber` 必填，避免把不同设备的运行时长相加。
5. `data_timeout` 使用后端当前监控配置的值，不在前端写死。

### HTTP 接口

新增：

```text
GET /api/sensor-history/operational-metrics
```

参数：

- `deviceNumber`：必填；
- `startTime`、`endTime`：沿用历史页 `YYYY-MM-DD HH:mm:ss` 格式，可选但必须成对出现；
- 未选择时间范围时，统计该设备数据库最新记录之前的 120 分钟，不无边界扫描全表。

响应继续使用 `{ code, message, data }`。参数非法返回 HTTP 400，设备不存在或范围内无数据返回成功的空指标。

同时更新 `docs/API.md`，写清“查询区间统计”和实时进程累计值的差异。

## 前端计划

1. 历史页筛选区下方、历史记录表格上方增加“运行指标”卡片区。
2. 展示两张汇总卡：水泵运行时长、加热运行时长，复用实时页的友好时长格式化逻辑。
3. 增加一张“出口水温每分钟变化”折线图，纵轴单位固定为 `℃/min`，零线清晰可见；悬浮提示显示分钟和精确数值。
4. 指标请求与列表、传感器趋势使用同一设备和时间条件；点击查询、重置或改变设备时三者一起刷新。
5. 分页切换只刷新历史表格，不重复查询汇总指标和趋势。
6. 指标加载失败时只清空指标区并显示局部错误，不清空已经成功返回的历史表格。
7. 保持 `1366×768` 和 `1920×1080` 桌面布局；不使用图片素材，不新增 WebSocket。

## 测试计划

### 后端单元测试

- 连续开启采样正确累计泵和加热时长；
- 当前采样关闭、未知或非法时不累计；
- 超过 `data_timeout` 的断档不累计；
- 查询开始边界只累计范围内秒数，结束边界之后不外推；
- 时间倒退、同时间重复数据和乱序输入不会重复累计；
- `0` 值不会被当成空值；
- 60 秒温度窗口、最小 5 秒跨度、升温、降温和非法温度处理正确；
- 每分钟只保留最后一个有效速率点。

### 仓储与 HTTP 测试

- 只查询 `field2`、`field6`、`field7` 和必要边界样本；
- 设备和时间条件参数化，字段列来自映射白名单；
- 多设备但未指定设备时返回 HTTP 400；
- 无数据返回 0 秒和空趋势；
- 接口响应结构与共享类型一致。

### 前端与验收

- 查询和重置时，列表、传感器趋势、运行指标使用同一条件；
- 分页不重复加载运行指标；
- 时长格式和实时页一致；
- 空数据、局部接口失败、升温和降温曲线显示明确；
- 运行相关测试和 `pnpm typecheck`，按项目约定不执行生产构建；
- 最后用真实 MySQL 做只读查询，并在两个目标分辨率下完成浏览器验证。

- 不新增运行时长数据库表，不迁移旧项目的 JSON 累计文件。
- 不修改 `t_sensor_data` 或 `t_sensor_field_mapper` 表结构。
- 不把操作日志中的下发指令当成设备实际运行状态。

- 不扩展未经确认的数据指标；后续若增加温差、流量或热功率，先单独确认统计口径。
