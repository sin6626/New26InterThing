# New26InterThing 分阶段重构计划

## 目标

在不修改现有数据库结构和设备协议的前提下，将旧项目重构为容易定位、修改、测试和回退的 TypeScript Monorepo。新旧系统按模块并行对照，不一次性切换。

## 第一里程碑：设备列表纵向闭环

交付内容：

1. pnpm workspace 与统一启动、构建、类型检查、测试命令。
2. Nuxt 前端和 Express 后端独立应用。
3. 后端读取现有 `t_device` 表，提供设备列表的筛选和分页接口。
4. Nuxt 设备管理页面展示查询、分页、加载和错误状态。
5. 前端控制台输出结构化 HTTP 调用信息。
6. 后端 API 行为测试、前后端类型检查和生产构建。

暂不包含新增、编辑、删除、MQTT、WebSocket、在线状态和控制逻辑。

## 验收标准

- 根目录执行 `pnpm dev` 可同时启动前后端。
- `GET /api/devices?page=1&pageSize=20` 返回统一格式的设备分页数据。
- 可按设备编号和设备名称模糊查询。
- 页面在 `1366×768` 与 `1920×1080` 下可正常查询和翻页。
- 测试不连接或写入真实 MySQL。
- `pnpm test`、`pnpm typecheck`、`pnpm build` 全部通过。

## 第二里程碑：实时数据通信闭环

### 目标

在不迁移控制逻辑的前提下，打通“设备 MQTT 上报 → 后端解析 → 现有数据库入库 → WebSocket 推送 → Nuxt 实时展示”的完整链路。第二里程碑只处理传感器实时数据，不下发任何设备指令。

### 兼容契约

- MQTT Broker 使用本机 Docker 中现有的 EMQX，配置继续从根目录 `.env` 读取。
- 订阅旧协议传感器主题 `device/sensor`。
- 设备编号继续使用 JSON 字段 `d_no`。
- 传感器物理字段到数据库字段的映射继续由现有 `t_sensor_field_mapper` 驱动，不在代码中写死比赛字段。
- 数据写入现有 `t_sensor_data`，不创建表、不增加字段、不修改表结构。
- 行为、错误、时间请求和指令主题不在本里程碑处理。

### 后端交付

1. 在 `infrastructure/mqtt` 中封装 MQTT 连接、订阅、断线重连和优雅关闭。
2. 在 `modules/realtime` 中解析传感器 JSON，校验 `d_no`，读取字段映射并生成入库数据。
3. 非法 JSON、缺失 `d_no` 或没有可映射字段时，记录清楚的错误并忽略该消息，服务继续运行。
4. 成功数据写入 `t_sensor_data`；上传时间缺失时沿用旧项目规则使用服务端时间。
5. 在 `infrastructure/websocket` 中维护浏览器连接，并在传感器入库成功后广播统一消息。
6. MQTT 和 WebSocket 随 Express 服务启动，在进程退出时释放连接。

### 共享消息类型

WebSocket 第一阶段只定义一种业务消息，放在 `packages/shared`：

```ts
interface SensorRealtimeMessage {
  type: 'sensor.realtime'
  data: {
    deviceNumber: string
    recordedAt: string
    fields: Record<string, string | number | null>
  }
}
```

若旧项目的实际数据类型与此定义冲突，以数据库字段映射和旧协议实测结果为准，不提前扩展通用事件系统。

### 前端交付

1. 启用“实时监控”导航并作为 `/` 默认首页。
2. 建立单一 WebSocket 客户端，支持连接、断开和有限间隔重连。
3. 页面显示 MQTT 状态、WebSocket 状态、当前设备编号和最近更新时间。
4. 根据后端推送的字段动态生成最新值卡片，不写死温度、压力、流量字段。
5. 切换设备时只展示所选设备的最新数据；没有数据和连接失败时提供明确空状态。
6. 暂不实现实时曲线，ECharts 留到历史与趋势里程碑。

### 已确认测试 seam

- MQTT 解析 seam：输入 Topic 和 Buffer，观察标准化结果或明确拒绝原因。
- 实时处理 seam：输入一条标准化传感器消息，观察仓储写入与 WebSocket 广播；数据库和连接使用替身，不写真实库。
- WebSocket seam：浏览器连接后能收到 `sensor.realtime` 消息，断开客户端不会影响服务。
- 前端继续执行 TypeScript 检查和生产构建，不为普通卡片组件堆单元测试。

### 验收场景

1. 启动现有 EMQX 后执行 `pnpm dev`，前后端均正常启动。
2. 设备向 `device/sensor` 发布合法旧协议 JSON，新后端成功入库并推送。
3. 实时页面无需刷新即可显示设备编号、时间和最新字段值。
4. 发布非法 JSON、缺失 `d_no` 和未知字段，后端不崩溃且不写入数据库。
5. MQTT Broker 重启后，后端自动恢复订阅并继续接收数据。
6. 浏览器刷新或短暂断网后，WebSocket 自动恢复连接。
7. 使用真实 Broker、真实 MySQL 做一次只读结构检查和受控单条消息联调；自动化测试不写真实数据库。
8. `pnpm test`、`pnpm typecheck`、`pnpm build` 全部通过。

### 明确不做

- MQTT 指令下发和操作日志。
- 设备新增、编辑、删除和在线/离线研判。
- 行为数据、错误数据和智能判定。
- 历史查询、实时曲线和 ECharts。
- PID、水循环状态机、安全保护和故障诊断。
- MQTT 仿真器与智能判定模拟器迁移。

## 第三里程碑：传感器历史数据闭环

### 目标

把旧项目的传感器历史数据页面重构为一个容易维护的纵向模块，打通“页面筛选 → 历史分页查询 → 动态字段展示 → 趋势查询与图表”的完整流程。继续读取现有 `t_sensor_data` 与 `t_sensor_field_mapper`，不修改数据库结构。

### 页面流程

1. 启用侧栏“历史数据”，路由使用 `/history`。
2. 页面首次进入时加载设备选项与传感器字段配置，然后按默认条件查询第一页历史数据和趋势数据。
3. 支持按设备编号、开始时间、结束时间和数据状态筛选；数据状态包括全部、正常（`vstatus = 0`）和告警（`vstatus != 0`）。
4. 点击查询时页码重置为 1，历史表格和趋势图使用完全相同的设备与时间条件。
5. 表格按 `c_time`、`id` 倒序分页，动态展示映射表中 `visible = '1'` 的字段，并保留设备编号、状态、是否在线和采集时间。
6. 趋势数据按分钟聚合并按时间正序展示，支持折线图、柱状图和散点图切换；默认显示最近 10 个点，可选择合理的点数上限。
7. 查询无结果、参数错误和接口失败时显示明确状态，不保留上一次查询的旧数据造成误判。

### 后端模块与接口

后端建立独立的 `modules/sensor-history`，接口只服务历史数据页面，不沿用旧项目可任意传入 `tableprefix` 的通用接口，避免动态表名和职责混乱。

1. `GET /api/sensor-history/options`
   - 返回设备编号选项和可见字段配置。
   - 字段配置包含稳定的协议键 `p_name`、中文名称、单位和数据类型。
2. `GET /api/sensor-history`
   - 参数：`page`、`pageSize`、可选 `deviceNumber`、`startTime`、`endTime`、`status`。
   - 返回统一的分页结构 `{ items, total, page, pageSize }`。
   - 数据库的 `field1` 至 `field10` 通过映射表转换为 `p_name`，页面不接触数据库列名。
3. `GET /api/sensor-history/trend`
   - 参数沿用列表筛选中的设备和时间条件，另加 `limit`。
   - 只聚合 `type = '1'` 且可见的数值字段，返回时间轴及动态 series。
   - `limit` 限制在 10 至 500，防止比赛时误请求过多图表数据。

所有筛选值使用参数化 SQL；只有经过白名单校验的 `field1` 至 `field10` 可以参与动态列查询。开始时间不得晚于结束时间，非法页码、状态或时间返回 HTTP 400。

### 共享类型

在 `packages/shared` 中增加历史页面直接使用的类型：

- `SensorHistoryField`：字段键、名称、单位和类型。
- `SensorHistoryItem`：设备编号、动态字段值、`vstatus`、在线标记和采集时间。
- `PaginatedSensorHistory`：历史数据分页结果。
- `SensorHistoryTrend`：时间轴与动态序列。

接口继续使用 `{ code, message, data }` 统一响应格式，不兼容旧接口中顶层 `status`、`total` 与任意 `tableprefix` 的混合结构。

### 前端交付

1. 在 `features/sensor-history` 内集中维护 API、查询状态和类型使用，页面只负责组合筛选区、表格和图表。
2. 使用 Element Plus 构建设备选择、日期时间范围、状态筛选、表格和分页，使用 Tailwind CSS 完成桌面端布局。
3. 表头与趋势序列根据后端字段配置动态生成，当前真实字段“压力、出水温度、入水温度、流量”不写死在组件中。
4. ECharts 封装为历史趋势组件，仅接收标准化时间轴、series 和图表类型；组件卸载时释放实例，窗口尺寸变化时正确调整。
5. 保留现有 HTTP 响应拦截器的结构化调用日志，能够看到历史页面请求参数和响应。

### 测试 seam

- 参数 seam：页码、点数、状态和时间范围能正确标准化或返回明确的 HTTP 400。
- 仓储 seam：设备、时间和状态筛选在 count 与 rows 查询中使用同一条件；分页参数和动态字段白名单正确。
- 映射 seam：数据库列能按现有 mapper 转成协议字段，数值 `0` 不会被当成空值，隐藏字段不返回。
- 趋势 seam：倒序查询结果转换为正序时间轴，空数据返回空数组，动态 series 名称和单位正确。
- HTTP seam：三个页面接口返回统一格式，仓储失败返回 HTTP 500。
- 前端执行 TypeScript 检查、生产构建和真实浏览器流程验证，不给普通展示组件堆无价值单元测试。

### 验收场景

1. 历史页首次打开能显示真实数据库中的动态表头、分页列表和趋势图。
2. 选择设备、时间范围和正常/告警状态后，列表总数、当前页数据与趋势条件一致。
3. 切换页码和每页数量只刷新列表，不意外重置筛选条件。
4. 折线图、柱状图和散点图切换正常，空结果时表格和图表均显示空状态。
5. 在 `1366×768` 与 `1920×1080` 下筛选区、表格、分页和图表不横向溢出。
6. 使用真实 MySQL 做只读查询验收；自动化测试不写真实数据库。
7. `pnpm test`、`pnpm typecheck`、`pnpm build` 全部通过。

### 明确不做

- 不修改 `t_sensor_data`、`t_sensor_field_mapper` 或添加索引。
- 不迁移旧项目可传入任意 `tableprefix` 的通用历史接口。
- 不提供导出、批量删除或历史数据编辑。
- 不迁移旧历史页的勾选与“识别”按钮；智能识别结果仍按约定留给后续行为数据页面。
- 不实现行为历史、错误历史、设备控制、操作日志或水循环分析。
- 不把实时监控页扩展成复杂分析大屏。
