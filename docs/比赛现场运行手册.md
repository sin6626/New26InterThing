# 比赛现场运行手册

[返回 README](../README.md)

## 启动前检查

```powershell
node --version
pnpm --version
docker ps
pnpm check:env
```

- MySQL 必须与 `contest_admin` 使用同一个 `DB_NAME`。
- MQTT Broker 使用 `.env` 中的地址、端口和凭据。
- 前端默认 `5174`，后端默认 `3001`。
- 识别接口使用 `apps/server/config/recognition.json`；`url` 为空时只会禁用行为识别。
- 首次启用故障来源功能时，在启动服务前执行 `pnpm migrate:error-source`；命令只创建来源旁表，不修改旧故障表。

## 启动与停止

```powershell
pnpm install
pnpm dev
```

启动后打开 `http://localhost:5174`，检查 MQTT、实时通道、设备编号和最新数据时间。MQTT 已连接只表示后端连上 Broker，不代表设备正在发数据。

停止时在 `pnpm dev` 窗口按 `Ctrl+C`，等待后端关闭 MQTT、WebSocket 和 MySQL 连接。

## 现场配置

| 配置 | 位置 | 检查要点 |
|---|---|---|
| 设备 | `t_device` | 设备编号唯一且与 MQTT `d_no` 一致 |
| 传感器字段 | `t_sensor_field_mapper` | `p_name` 匹配报文键，`db_name` 仅为 `field1`~`field10` |
| 行为字段 | `t_behavior_field_mapper` | 与赛方识别响应键一致 |
| 控制参数 | `t_direct_config` + `t_direct_global` | 目标温度低于安全上限；PID 周期不小于最短开/关时间之和 |
| 水力阈值 | 同上 | `min_operating_pressure < max_safe_pressure`，正常工况在安全区间 |
| 故障映射 | `t_error_code_mapper` | 安全和水力诊断码有可读中文信息 |
| 识别适配 | `apps/server/config/recognition.json` | 只按赛方正式文档填写，改后重启后端 |

## 正常与调试模式

- 正常模式用于真实设备和故障测试，安全保护、数据新鲜度和故障锁均生效。
- 调试模式在右上角开启，用于模拟切换自动/手动和调参；它会跳过安全锁和自动启动数据校验，不能用来验证空转、堵塞等保护。
- 调试模式只存在当前后端进程，重启后默认关闭；它不影响历史数据的 `vstatus` 判定。

## 复位、清零和真实控制

- 故障复位要求传感器数据新鲜且安全，水泵/加热的实际与期望状态均关闭；复位后仍保持停止。
- 累计水量清零会修改 `t_water_flow_accumulator` 并写操作日志，不发 MQTT。
- 开泵、加热和时间同步会发布 MQTT。未确认管路、供水和人员安全前不操作。

## 排查顺序

1. **页面**：查看调试状态、MQTT/WebSocket/设备状态和最新时间。
2. **HTTP**：查看浏览器控制台的 JSON 请求日志，确认方法、URL、头、参数、状态码和响应。
3. **WebSocket**：确认 `/ws` 已连接；断开会导致页面不实时刷新，不代表 MQTT 未入库。
4. **MQTT**：确认 Broker 和凭据，设备在 `device/sensor` 发送带 `d_no` 的 JSON，指令回报使用 `device/direct`。
5. **MySQL**：确认字段映射与报文键一致，再查相应表是否产生新记录。

| 现象 | 优先检查 |
|---|---|
| MQTT 已连接但设备离线 | 设备是否持续发 `online=0` 的 `device/sensor` |
| 后端提示缺少 `d_no` | 可能是 `device/direct` Modbus 回报，或传感器报文字段不正确 |
| 自动模式无法启动 | 正常模式查数据新鲜度和故障锁；纯模拟可开调试模式 |
| 复位失败 | 按“当前限制”检查压力、流量、温度和执行器 |
| 历史告警不增加 | 关泵零流量是正常；查是否超温、超压或开泵低流量 |
| 行为识别返回 422 | 检查 `recognition.json` 和赛方正式接口文档 |
